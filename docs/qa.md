# QA: backend-автоматизация Marketplace

Go E2E проверяет работающий HTTP API и состояние PostgreSQL в Compose. Цель — обнаружить потерю остатков,
денег, квоты промокода и нарушение доступа; Allure связывает результат с отдельным бизнес-кейсом.
[OpenAPI](../catalog-service/internal/api/openapi.yaml) задаёт HTTP-контракт,
[технические решения](hw2-design.md) — правила транзакций и расчётов.

## Уровни проверок и приоритеты

| Уровень | Реализовано | Граница доказательства |
|---|---|---|
| Go unit/HTTP tests | JWT, валидация, точные деньги, переходы, ownership, middleware, маскирование логов | Изолированные проверки не доказывают транзакции PostgreSQL |
| Go E2E | HTTP → приложение → PostgreSQL: 11 групп исходной приёмки, проверки отката и трёх конкурентных конфликтов | Это локальный Compose; не production и не нагрузочный тест |
| Проверки инфраструктуры тестов | Конфигурация Compose, область фикстур, HTTP/отчётность и маскирование | Не заменяют проверку бизнес-сценария |
| CI | Отдельные проверки Go и запуск E2E; результаты сохраняются как artifacts | Успех подтверждает конкретный run |

P0 — деньги, атомарность и конкурентный резерв: ошибка может испортить данные.
P1 — роли, владение, жизненный цикл, промокоды и ограничение частоты: ошибка нарушает бизнес-правило или доступ.
P2 — навигация, Swagger и диагностика: ошибка затрудняет использование или расследование.
Это порядок разбора риска; весь набор нужен перед принятием изменений заказа.

Существующие unit-тесты не обращаются к настоящей PostgreSQL. Отдельные интеграционные тесты хранилища,
автоматическая проверка всех ответов по OpenAPI, fuzzing и нагрузочный эксперимент пока запланированы.
Их нельзя учитывать как уже выполненное покрытие.

## Требование → риск → критерий → тест

Стабильный ID идентифицирует кейс в Allure. ID фикстуры и UUID результата меняются при запуске.
Все E2E входят в TestMarketplace. В таблицах указаны путь группы и диапазон стабильных ID;
полное имя кейса включает читаемый суффикс, а табличные случаи — дополнительный уровень с ID.
Группа Logs выполняется последней и проверяет запросы всех предыдущих групп.

|---|---|---|---|

## Техники тест-дизайна

Граничные значения: длина name 0/256, description 4001, category 0/101; stock −1 и возврат через границу
INTEGER; price 0, 1.001 и 0.29; size 0/101, quantity 0/1000, 51 позиция. Текущий набор проверяет эти
представители, но не все пары «нижняя граница / сосед / верхняя граница / сосед» каждого поля.
Классы эквивалентности: допустимый, отсутствующий, null, неверного формата и дублирующий ввод;
товар ACTIVE/INACTIVE/несуществующий; токен access/refresh/повреждённый/отсутствующий.

RBAC проверяется по роли и владению: USER, свой SELLER, чужой SELLER, ADMIN, чужой покупатель.
Матрица покрывает выбранные сочетания ролей и маршрутов.
Граф состояний: CREATED → PAYMENT_PENDING → PAID → SHIPPED → COMPLETED;
CREATED/PAYMENT_PENDING → CANCELED. Есть запрещённый пропуск этапа, запрет update вне CREATED,
повторная отмена и запрет отмены после оплаты. Все возможные пары состояний E2E не перебирает.

Таблица решений для промокода связывает условие и результат:

| Условие | Результат |
|---|---|
| Процент 70 / 71 | Скидка 70% / полная цена |
| Фиксированная скидка больше суммы | К оплате 0 |
| Сумма update ниже минимума | Скидка снимается, использование возвращается |
| Промокод выключен или истёк к update | 422 и откат |
| Квота 1 занята этим же заказом | Update не занимает вторую квоту |
| Два create претендуют на последнюю квоту | Один 201, один 422; использование равно 1 |

HTTP-проверки дополнены SQL-инвариантами: остаток не теряется при отказе и возвращается при
отмене; неуспешная операция не создаёт заказ/операцию; update не оставляет часть нового резерва;
только один активный заказ на пользователя; счётчик промокода соответствует занятой квоте.
Конкурентный сценарий не предполагает, какой запрос победит. Два одновременных запроса проверяют
конкретную гонку, но не доказывают отсутствие всех гонок или производительность системы.

## Запуск и разбор падения

```bash
make check
make up
make e2e
# Для HTML: Node.js >= 24; npm ci один раз в корне
make e2e-report
make e2e-open
```

Для проверки одной группы после `make up`:

```bash
make e2e E2E_GO_FLAGS="-v -run TestMarketplace/DiscountedOrderAmounts"
```

Такой фильтр выполняет только выбранную группу. Проверка логов всех запросов требует полного запуска.

Команды запуска и настройки Docker описаны в [README](../README.md#запуск-и-проверки).
E2E не поднимает приложение автоматически. Данные имеют отдельный префикс запуска; набор сохраняет их
для проверки SQL. Повторный запуск использует новые данные, но не очищает named volume.
Фикстуры и размер БД накапливаются. Сдвиг времени истории операций касается только пользователей запуска.

Последний RUNID находится в `artifacts/e2e/latest-run`. В соответствующем каталоге лежат:

- allure-results — отдельные результаты бизнес-кейсов и вложения;
- run.json — параметры и сведения запуска;
- fixtures.json — созданные пользователи, товары, заказы и промокоды;
- application.log — очищенные логи приложения.

При падении сначала найдите кейс по стабильному ID, затем первый failed step, HTTP-ответ и SQL snapshot.
Сопоставьте X-Request-Id с application.log. Ошибку транспорта или недоступную БД отличайте от нарушения
бизнес-критерия. Повтор изменяющего запроса может создать новые данные: автоматические повторы не нужны.
Сохраняйте исходный failed run перед повтором. HTML — способ просмотра; код выхода Go определяет результат.
CI запускается на pull request и push в main на Ubuntu 24.04: сначала Go-проверки, затем Compose E2E.
Для CI используется отдельное имя Compose-проекта; его volume удаляется после запуска.
Go JSONL, результаты, логи, manifest и доступный HTML сохраняются и при падении тестов.
Успешная генерация HTML не превращает тест в passed. Статус конкретного CI-run нужно смотреть отдельно.

## Регрессии и следующие шаги

Регрессионные сценарии защищают ранее исправленные ошибки:
проверку диапазона денег нужно выполнять после применения скидки, отдельно для total и discount;
cooldown должен отсчитываться после сохранения успешной операции. Первый различает допустимые
6/9 млрд после скидки и недопустимое переполнение, второй сравнивает время операции с созданием/обновлением
заказа и проверяет повторный запрос. Это регрессионные тесты существующего поведения.
Они не доказывают, что исходные исправления выполнялись через ATDD, и не означают наличие открытых дефектов.

Аудит логов также поймал отрицательную duration при коррекции часов локальной VM. Для измерения
сохранено монотонное время; UTC применяется только при форматировании timestamp. LOG-001 проверяет duration ≥ 0.

План расширения, ещё не реализованный:

1. Проверять ответы по OpenAPI: status, headers и schema положительных/отрицательных ответов.
2. Добавить интеграционные тесты транзакций на PostgreSQL: rollback и блокировки без полного HTTP setup.
3. Fuzzing JSON, точных денежных значений и рекурсивного маскирования; инварианты — отсутствие panic,
   записи вне денежных ограничений и секретов в результатах. Сначала сохранить минимальные найденные контрпримеры.
4. Провести отдельный нагрузочный эксперимент. Зафиксировать CPU/RAM, версии Go/PostgreSQL, число реплик,
   данные, прогрев, длительность, RPS и конкуренцию. Измерять p95 и долю ошибок отдельно по маршрутам,
   отличая ожидаемые бизнес-отказы от 5xx/transport errors; пороги согласовать до эксперимента.

Следующая учебная история для настоящего ATDD — фильтр каталога по цене. До реализации согласовать
примеры: 99.99/100.00/100.01 при минимуме 100.00; включение обеих границ диапазона; min > max → 400;
пустой результат; совместимость с category/status и пагинацией. Затем написать приемочный тест,
увидеть его падение из-за отсутствия поведения (red), реализовать минимальный фильтр и получить green.
Семантика фильтра и эти примеры пока предложение; такой функциональности и такого red/green цикла ещё нет.
